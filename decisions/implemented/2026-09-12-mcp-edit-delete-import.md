# 编辑 / 删除 / 从其它 Agent 导入（v0.6.1）

## 背景

v0.6.0 把插件的可见性模型做完了（四档曝光 + 预设运行时隔离），但配置管理仍是「只能加、不能改、不能删」：面板只有「添加 MCP」（粘贴 JSON），用户要从别处搬配置、或修正一条加错的命令，只能去手工编辑 `cordis.patch.yml` 与 `.dsh/mcps/mcp.json`。

## 决策

### 1. 编辑/删除的写回矩阵（按行来源）

| 行来源 | 真实目标文件 | 依据 |
| --- | --- | --- |
| 全局行（loader 行） | `cordis.patch.yml` | profile patch 的 `- insert:` 行加载后归属**根树**，其 `tree.filename` 是每次启动被重置为 `[]` 的 `cordis.yml`；写它无意义，必须映射到同目录 patch 文件（`materializeTargetOf`） |
| 项目行 | `<workspace>/.dsh/mcps/**/mcp.json` | 挂载名带路径哈希后缀（`projectServerName`），用 `findProjectMcpFile` 反查原始键 |
| 预设组合行 | `<preset>/agent.cordis.yml` | **只读**：运行期写它会触发 standing 重挂事故（旧组合不 dispose → serverName 冲突 → 会话创建失败） |

### 2. 「先写文件、再动运行时」

文件是真相，运行时是缓存。顺序反了会出现「运行时改了但没落盘」的半状态（用户以为成功、重启后回到旧配置）。因此：文件写成功后，`loader.remove/update`、`remountWorkspace` 一律容错 —— `patchReload: live` 的 profile 可能已经按新文件内容重建了行，重复操作会抛「未知 id / 行已不存在」，那属正常。

### 3. 文本级改写而非 YAML 库

这些文件承载用户的注释、`!!js` 表达式与手工排版，YAML 库的 `dump` 会全部丢掉。因此新增 `domain/composition-file.ts` 做纯文本的行块操作（定位 / 删除 / config 键读写 / 缩进行标志），并把它做成零依赖模块供真值表自测。

### 4. 动态（`!!js`）字段只读

`env`/`headers` 里可能是 `!!js '`${process.env.KEY}`'` 这类表达式。若编辑表单直接读「loader 求值后的值」再写回，就会把表达式固化成**明文密钥**（从别的 agent 导入的 `${VAR}` 尤其危险）。因此：表单对含 `!!js` 的键只读展示，写回时取该键的原文（`dedentLines(readConfigBlock().lines)`）。

### 5. 预设组合行只读，用「关闭」档位替代删除

删除需要改 `agent.cordis.yml`，而运行期写它必然触发重挂事故（同上）。选项有二：(a) 只读 + 引导用「关闭」档位；(b) 排队到下次启动时物化（多一套行级待生效机制）。选 (a)：对「让它不可用」这个实际目的而言，「关闭」档位已经等效（模型看不到、`mcp_search` 搜不到、`mcp_call` 拒绝），唯一差别是进程/连接仍占着；而 (b) 的复杂度与「点了删除不立即生效」的困惑不值得。

### 6. 项目行不支持改名

项目行的名字由 `.dsh/mcps` 下的配置键决定，运行时挂载名额外带 `<8位路径哈希>` 后缀。允许面板改名会把「文件键 / 挂载名 / 策略键」三者关系搞乱（改一个键要同时改三处且哈希要重算）。改名的低频需求交给直接编辑文件。

### 7. 导入复用 `/mcp/add`

`domain/external-import.ts` 只负责「嗅探形态 + 归一化字段」，归一化结果仍以 `mcpServers` JSON 交给既有的 `/mcp/add`（自带「已存在跳过 / 挂载失败报告 / 全局写 patch + 项目写 mcp.json」）。这样不会出现第二套落盘逻辑，导入与手工粘贴走同一条路径。导入后如需设档位，前端再对新挂载名批量调 `/policy`（`/mcp/add` 因此新增回传 `names`）。

### 8. 顺手修的三个 v0.6.0 缺陷

1. **全局行的停用状态从未落盘**：`syncPresetFiles` 跳过 `basename(file) === 'cordis.yml'`，而 patch 行正属于根树 → 「隐藏/关闭」档位的进程停用意图重启后丢失（可见性仍正确，因为装配层按策略过滤）。改为映射到同目录 patch 文件。
2. **`null` 歧义**：`rowFlagAt` 的 `null` 同时表示「文件里没有该行」与「有该行但没有 `disabled` 键」，而调用方把 `null` 一律当「行不存在」跳过 → 标志永远写不进去。改为先 `findRowBlock` 判存在、再把无键归一为 `false`。
3. **`setRowFlag` 不认缩进行**：旧实现用 `^- id:` 匹配，对 patch 文件的 `    - id: mcp-x` 无效。统一到 `setRowFlagAt`（支持任意缩进）。

## Alternatives

| 方案 | 为什么不选 |
| --- | --- |
| 用 YAML 库解析 + 重新序列化配置源文件 | `yaml.dump` 丢掉注释与 `!!js` 原排版，等于破坏用户文件 |
| 编辑表单直接读写「loader 求值后的 config」 | 会把 `${VAR}` 表达式固化成明文密钥 |
| 预设组合行也支持删除（排队到重启物化） | 多一套行级待生效机制，且「点了删除不立即生效」易困惑；「关闭」档位已能达到目的 |
| 项目行允许改名 | 文件键 / 挂载名（含路径哈希）/ 策略键三者需同步重写，收益低风险高 |
| 为导入单独做一套落盘端点 | 与 `/mcp/add` 的「已存在跳过 / 挂载失败」逻辑重复，必然漂移 |
| 扫描时同时支持 TOML（Codex）与 Zed 的 `context_servers` | 需要引入 TOML 解析与又一套形态；本版本在扫描结果里标注「已跳过」，留待有需求时再加 |

## Consequences

- 面板从「只能加」变成「能管」：改命令行、换 URL、修 env、删掉不用的 MCP 都在面板内完成，无需手工编辑 YAML。
- 编辑是**就地改写**用户文件（局部替换），不会被格式化或丢注释；含动态表达式的字段保持不变。
- 新增三个纯逻辑模块与三个自测（`composition-file` / `external-import` / `mcp-edit`），文本编辑与格式导入的语义都被真值表锁住。
- 已知边界：预设组合行只读、项目行不可改名、导入不跟踪源文件变化、不支持 TOML。
